# EKT API: статус исследования

Статус: **частично исследован сохранённый ответ списка; live-проверка исполнителем не завершена**. Доступен `local-evidence/products-page-1.json`: 20 товаров, структура и поля описаны в [docs/EKT_DATA.md](../../docs/EKT_DATA.md). Файл не содержит HTTP status и времени запроса, поэтому их нельзя восстановить из JSON.

В актуальном Issue #2 партнёр указал `https://ekt.kz` и передал автору задачи документ с логином/паролем. В доступной рабочей папке этого документа нет, переменные `EKT_API_BASE_URL`, `EKT_API_USERNAME`, `EKT_API_PASSWORD` в окружении исполнителя не настроены. Это отсутствие локальной конфигурации, а не отсутствие выданного партнёром доступа. Авторизованные запросы исполнителем не повторялись.

Источник известных путей: Issue #2. Это требования к проверке, а не результаты наблюдения API.

## Инструмент исследования

Реализован Kotlin CLI в пакете `catalog.cli`, повторно использующий `EktConfig`, `EktRawClient` и транспорт. Команды `list`, `list --page`, `detail --id` и `--output` позволяют получить и сохранить реальный JSON без временного кода и отдельной curl-интеграции. [Точные команды, настройка окружения и коды выхода](../README.md#cli-получение-данных-из-терминала).

CLI и тесты не определяют схему товара. Проверки с синтетическим транспортом покрывают запросы, справку без окружения/сети, ошибки аргументов, JSON stdout, отдельную диагностику, экспорт без перезаписи, ошибки HTTP/таймаута/JSON/записи и отсутствие секретов в диагностике. Это не подтверждение живой интеграции.

Локальная проверка 2026-09-23: `gradle :catalog-service:test :catalog-service:installDist` завершилась успешно; 13 тестов CLI, 11 тестов транспорта и 5 тестов существующего HTTP-каркаса прошли. Проверены `gradle --quiet :catalog-service:run --args='--help'` и запуск справки из дистрибутива без переменных EKT (код 0). Команда `list` из дистрибутива без конфигурации вернула код 2 и безопасное сообщение о недостающем `EKT_API_BASE_URL`. Это локальная проверка, не запрос к EKT.

Live-блокер сохраняется: выданные credentials ещё не доступны процессу. Адрес известен: `https://ekt.kz`. Запускник `bash catalog-service/bin/ekt-cli list` позволяет оператору ввести логин и скрытый пароль при запуске и передаёт их Kotlin CLI через окружение. Проверки реального API ниже остаются невыполненными; Product, нормализатор и публичный адаптер должны опираться на полученные позже факты.

Запускник проверен локально: синтаксис Bash, справка без credentials, отказ без терминала с кодом 2, интерактивный ввод в PTY без эха пароля и передача введённых значений в Kotlin-валидацию. Использовались только синтетические невалидные credentials, отклоняемые до сети; реальная аутентификация EKT этим не подтверждается.

При предоставлении доступа получить default list, страницы 1 и 2, повтор страницы 1 и детали нескольких обнаруженных ID. Сохранять каждое наблюдение под новым именем, фиксировать время, статус из stderr и структуру из JSON. Для безопасного failure case запросить неизвестный ID; отказ CLI без переменных окружения является локальной ошибкой конфигурации и не считается проверкой EKT без авторизации. Намеренно неавторизованные запросы и неположительные страницы требуют отдельной проверки в #2: обычный CLI валидирует такие входы до сети. Тела ошибок источника CLI не экспортирует ради безопасной диагностики; их структуру ещё нужно исследовать отдельно. Не считать эти пункты выполненными по тестам CLI.

## План воспроизводимой проверки после получения доступа

Для каждого запроса записать дату, endpoint без credentials, HTTP status, Content-Type, форму JSON и фактические поля. Сырые ответы держать в игнорируемом `local-evidence/`; в Git добавлять только проверенные fixtures без секретов. Не включать Authorization или конфигурацию в журнал запросов.

| Запрос | Что проверить | Результат |
| --- | --- | --- |
| `/api/products` | Обёртка, коллекция, ID, SKU, название, категория, цена, наличие, бренд, изображения | Не проверено |
| `/api/products?page=1` | Нумерация, размер, метаданные пагинации | Исследован сохранённый JSON: page=1, per_page=20, count=20, 20 items; HTTP status и полнота каталога не установлены |
| `/api/products?page=2` | Другая страница, пересечения ID, общее число | Не проверено |
| Повтор страницы 1 | Стабильность идентификаторов | Не проверено |
| Невалидная и выходящая за пределы страница | Статус и форма ошибки / пустой страницы | Не проверено |
| `/api/products/detail?id={id}` для нескольких ID из списка | Поля деталей и совпадение ID; разные категории при наличии | Не проверено |
| Неизвестный и невалидный ID | Статус и форма ответа | Не проверено |
| Запрос без Authorization | Статус и форма ответа | Не проверено |
| Запрос с неверным Authorization, если безопасно | Статус и форма ответа | Не проверено |

## Поля и преобразование

Наблюдаемые поля сохранённого списка, их типы, заполнение, пример и ограничения описаны в [docs/EKT_DATA.md](../../docs/EKT_DATA.md). Детали товара пока не исследованы; отсутствие поля в списке не доказывает его отсутствие в API.

После исследования для каждого поля описать raw JSON path, исходный тип и семантику, нормализованное имя и тип, правила обработки null/пустых/невалидных значений, различия list/detail и пример из проверенного ответа.

## Наблюдение по карточкам товаров

При анализе карточек обнаружены два варианта наполнения. У части товаров отдельный раздел «Характеристики» заполнен структурированными значениями. У других товаров этот раздел пуст, а имеющиеся сведения находятся только в разделе «Описание».

Следствия для адаптера и будущего Product:

- пустой раздел характеристик не означает, что у товара нет технических сведений;
- описание и характеристики нужно сохранять как разные исходные поля с указанием источника;
- свободный текст описания нельзя автоматически выдавать за подтверждённые структурированные характеристики;
- отсутствие характеристики должно оставаться отличимым от значения, извлечённого вручную или недоступного в ответе;
- при подборе аналогов нельзя считать совпадением данные, которые присутствуют лишь в неструктурированном описании, пока правило их извлечения и проверка не определены.

Нужно дополнительно зафиксировать raw JSON path, тип и заполнение обоих разделов на нескольких карточках. Это наблюдение о содержимом карточек не устанавливает единый контракт detail-endpoint до сохранения и проверки реальных ответов.

Особенно проверить валюту и точность цены, единицы и семантику остатков, складские разрезы, структуру характеристик и сертификатов. Не переводить неизвестный остаток в ноль и не приравнивать отсутствие цены к бесплатному товару. Сохранять структуру характеристик, если API предоставляет пары ключ/значение. Не угадывать единицы, валюту и совместимость.

## Подготовка поиска аналогов

В списке наблюдаются `article`, `name` и `price`; возможное использование и ограничения описаны в [docs/EKT_DATA.md](../../docs/EKT_DATA.md). Структурированные характеристики совместимости и наличие пока не установлены. Следующие пункты — вопросы исследования, не обещание поддержки:

- Можно ли использовать категорию/тип и структурированные параметры как обязательные фильтры?
- Достаточно ли достоверны остатки для фильтра доступности; известны ли склад и единицы?
- Какие характеристики, бренд, описание и цена подходят для ранжирования?
- Какие значения отсутствуют или противоречат друг другу между list/detail?
- Потребуются ли словари единиц и синонимов, индексирование, embeddings или гибридный поиск?

Будущий AI должен сравнивать нормализованные факты и повторно проверять предлагаемые аналоги по каталогу. Поиск, выбор аналогов, корзина и checkout предоставленными endpoints не подтверждены.

## Передача в Issue #3

Доступен Gradle-модуль `:catalog-service` с конфигурацией, внутренним транспортом и тестами. После исследования остаётся добавить типизированные raw-модели, нормализованный Product, mapping, публичный адаптер с list/detail и проверки соответствия исходным значениям. До этого Issue #3 не должен использовать внутренний JSON-клиент как доменную границу.

HTTP/Ktor API, база товаров, AI, UI и корзина в этой задаче не реализуются.
