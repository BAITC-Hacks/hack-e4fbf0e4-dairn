# EKT API: статус исследования

Статус: **unverified**. Реальные запросы пока не выполнены: в окружении разработки отсутствуют `EKT_API_BASE_URL`, `EKT_API_USERNAME`, `EKT_API_PASSWORD`.

Источник известных путей: Issue #2. Это требования к проверке, а не результаты наблюдения API.

## План воспроизводимой проверки после получения доступа

Для каждого запроса записать дату, endpoint без credentials, HTTP status, Content-Type, форму JSON и фактические поля. Сырые ответы держать в игнорируемом `local-evidence/`; в Git добавлять только проверенные fixtures без секретов. Не включать Authorization или конфигурацию в журнал запросов.

| Запрос | Что проверить | Результат |
| --- | --- | --- |
| `/api/products` | Обёртка, коллекция, ID, SKU, название, категория, цена, наличие, бренд, изображения | Не проверено |
| `/api/products?page=1` | Нумерация, размер, метаданные пагинации | Не проверено |
| `/api/products?page=2` | Другая страница, пересечения ID, общее число | Не проверено |
| Повтор страницы 1 | Стабильность идентификаторов | Не проверено |
| Невалидная и выходящая за пределы страница | Статус и форма ошибки / пустой страницы | Не проверено |
| `/api/products/detail?id={id}` для нескольких ID из списка | Поля деталей и совпадение ID; разные категории при наличии | Не проверено |
| Неизвестный и невалидный ID | Статус и форма ответа | Не проверено |
| Запрос без Authorization | Статус и форма ответа | Не проверено |
| Запрос с неверным Authorization, если безопасно | Статус и форма ответа | Не проверено |

## Поля и преобразование

Подтверждённых реальными ответами полей нет. Нельзя утверждать, что какое-либо поле отсутствует: его наличие пока неизвестно.

После исследования для каждого поля описать raw JSON path, исходный тип и семантику, нормализованное имя и тип, правила обработки null/пустых/невалидных значений, различия list/detail и пример из проверенного ответа.

Особенно проверить валюту и точность цены, единицы и семантику остатков, складские разрезы, структуру характеристик и сертификатов. Не переводить неизвестный остаток в ноль и не приравнивать отсутствие цены к бесплатному товару. Сохранять структуру характеристик, если API предоставляет пары ключ/значение. Не угадывать единицы, валюту и совместимость.

## Подготовка поиска аналогов

Подтверждённых полей для фильтрации и ранжирования пока нет. Следующие пункты — вопросы исследования, не обещание поддержки:

- Можно ли использовать категорию/тип и структурированные параметры как обязательные фильтры?
- Достаточно ли достоверны остатки для фильтра доступности; известны ли склад и единицы?
- Какие характеристики, бренд, описание и цена подходят для ранжирования?
- Какие значения отсутствуют или противоречат друг другу между list/detail?
- Потребуются ли словари единиц и синонимов, индексирование, embeddings или гибридный поиск?

Будущий AI должен сравнивать нормализованные факты и повторно проверять предлагаемые аналоги по каталогу. Поиск, выбор аналогов, корзина и checkout предоставленными endpoints не подтверждены.

## Передача в Issue #3

Доступен Gradle-модуль `:catalog-service` с конфигурацией, внутренним транспортом и тестами. После исследования остаётся добавить типизированные raw-модели, нормализованный Product, mapping, публичный адаптер с list/detail и проверки соответствия исходным значениям. До этого Issue #3 не должен использовать внутренний JSON-клиент как доменную границу.

HTTP/Ktor API, база товаров, AI, UI и корзина в этой задаче не реализуются.
