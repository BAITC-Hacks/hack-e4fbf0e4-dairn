# AI-предвалидация каталога (Issue #5)

Реализован отдельный пакет `kz.hackalem.catalog.prevalidation` в существующем модуле.
Он принимает одну сырую запись товара и возвращает исходную запись вместе с отдельным
рекомендательным отчётом либо явной категорией сбоя. Он не создаёт Product и не изменяет
цену, остаток, характеристики или другие факты. Ktor-маршруты и EKT CLI не вызывают его
автоматически: подключение к нормализатору ожидает результаты #2.

## Настройка

Переменные окружения процесса (файл `.env` автоматически не загружается):

| Переменная | Значение |
| --- | --- |
| `OPENAI_PREVALIDATION_ENABLED` | `false` по умолчанию; только `true` включает клиент |
| `OPENAI_API_KEY` | Обязательный секрет при включении; только environment |
| `OPENAI_MODEL` | Обязательная модель с поддержкой Structured Outputs; выбирается явно |
| `OPENAI_TIMEOUT_MS` | 30000 по умолчанию, 1–120000; полный срок запроса, включая тело |
| `OPENAI_MAX_OUTPUT_TOKENS` | 2048 по умолчанию, 256–8192 |

Используется `POST https://api.openai.com/v1/responses`, `store=false`, строгая JSON Schema.
Редиректы запрещены, автоматических повторов нет. Таймаут подключения — 10 секунд,
общий срок ограничен указанным выше таймаутом. Успешное тело ограничено 256 KiB,
тела HTTP-ошибок отбрасываются. Сырые данные и выбранный JSON-вход ограничены каждый
64 KiB, число выбранных путей и разрешённых целевых полей — по 100.

Клиент блокирующий; запускать на IO worker, не на event loop Ktor. Другой провайдер
подключается реализацией `CatalogPrevalidator`; секрет OpenAI не пересылается на произвольный URL.
`store=false` не следует трактовать как обещание отсутствия любой обработки/хранения у провайдера.

## Входная граница и использование

`RawCatalogRecord` получает локальный `recordId` для корреляции, `JsonObject` одной записи,
явный список разрешённых JSON pointers и список разрешённых полей Product. Локальный ID
не является доказательством идентичности товара EKT. Снимок raw отделён от изменяемых
коллекций вызывающего кода; его строковое представление скрыто.

Разрешённые пути должен выбирать доверенный код интеграции #2 после исследования схемы.
Нельзя передавать целый HTTP-ответ с заголовками, credentials, данные покупателей/сессий.
Клиент дополнительно отклоняет чувствительные имена выбранных полей, вложенные секретные
поля, узнаваемые credentials и собственный API key. Эти проверки не заменяют отбор данных:
произвольный секрет под обычным именем поля невозможно надёжно распознать эвристикой.

Пример **синтетический**, не контракт EKT:

```kotlin
val validator = OpenAiPrevalidator.fromEnvironment()
val input = RawCatalogRecord(
    recordId = "local-observation-1",
    raw = rawProductJson,
    fieldPaths = setOf("/name", "/stock", "/price"),
    normalizedFields = emptySet(), // Пока Product из #2 не определён, mappings запрещены.
)
val result = validator.validate(input)
val original = result.source.raw // Источник для будущего детерминированного нормализатора.
when (val outcome = result.outcome) {
    is ValidationOutcome.Completed -> reviewAdvisoryReport(outcome.report)
    is ValidationOutcome.Failed -> recordFailure(outcome.category)
}
```

`reviewAdvisoryReport` и `recordFailure` здесь обозначают код потребителя, не готовые методы.
Никакие hints не исполняются автоматически. В будущем нормализатор должен применять только
свои явно разрешённые и проверяемые правила к исходным значениям. Отсутствие успешного AI
отчёта не мешает читать raw и не означает, что исходные данные пригодны для нормализации.

В модель отправляется проекция вида `pointer -> {present, value}`. Отсутствующее поле,
явный `null` и число `0` различимы. Переданная информация об актуальности не переписывается;
модель не получает права объявить устаревший остаток актуальным.

## Выходной контракт

Единый объект `ReportContract.schema` используется в запросе и локальном валидаторе.
Все поля обязательны; лишние поля, неверные типы/enum, числовые строки вместо чисел
и confidence вне `[0,1]` отклоняются. Массивы ограничены 100 элементами,
строки отчёта — 1–2000 символами. Локальные лимиты строже базовой схемы провайдера.

- `recordId`: точное совпадение с локальным ID входа.
- `status`: `valid`, `needs_normalization`, `ambiguous`, `insufficient_data`.
- `issues[]`: `field`, `type`, `message`, `severity`; типы `missing`, `ambiguous`,
  `inconsistent_format`, `unit_issue`, `suspicious_value`, `mapping_uncertain`;
  severity `info`, `warning`, `error`.
- `mappingSuggestions[]`: `sourceField`, `targetField`, `confidence`, `reason`.
- `normalizationHints[]`: `field`, `operation`, `reason`; операции `trim_whitespace`,
  `parse_number`, `parse_boolean`, `normalize_unit`, `domain_review`.
- `requiresReview`: boolean.

Issues могут ссылаться только на выбранные пути, включая отсутствующие. Mapping/hint
требуют выбранного существующего non-null значения; targetField — явно разрешённого поля
контракта Product. `ambiguous`, `insufficient_data` и error-issues требуют review.
`valid` несовместим с issues, hints и review. Даже валидный по схеме отчёт остаётся
мнением AI: схема не доказывает истинность его объяснений или правильность соответствий.
В отчёте нет полей для исправленных значений и нет метода применения преобразований.

## Ошибки и обход AI

`ValidationOutcome.Failed` содержит только категорию, никогда текст исключения или тела ответа:

- `disabled`, `configuration` — выключено или неверная конфигурация;
- `insufficient_input`, `unsafe_input`, `input_too_large` — запрос не отправлен;
- `timeout`, `interrupted`, `transport`, `api_error`, `response_too_large` — сбой вызова;
- `refusal`, `incomplete_response`, `invalid_response`, `schema_validation` — отчёт не принят.

Исходная запись сохраняется при каждом таком результате; фиктивного успешного отчёта нет.
Прерывание потока сохраняет interrupted flag; отмена coroutine/операции пробрасывается.
Сбой не подменяется `status=valid` или пустым списком проблем.

`result.metadata()` предоставляет безопасные метаданные для логирования: локальный ID,
статус, число/типы замечаний, review либо категорию сбоя. Полные записи, объяснения AI,
HTTP-заголовки и ключи автоматически не логируются. OpenAI-клиент записывает только эти
метаданные через `java.util.logging` на уровне `FINE` (включается настройкой логирования).
Для выключенного/неверно настроенного клиента потребитель может использовать `metadata()`.
Не логировать `raw` и request objects.

## Проверка и оставшиеся зависимости

```sh
gradle :catalog-service:test
```

Синтетические fixtures в `src/test/resources/prevalidation/synthetic-records.json` покрывают
условно заполненный товар, пропуски, неизвестный stock, разные формы характеристик,
неоднозначную единицу и пустую запись. Они **не являются реальными EKT fixtures**.
Тесты используют подменённый транспорт и локальный HTTP-сервер, без платных запросов.

Для завершения #5 ещё нужны:

1. Проверенные примеры EKT и разрешённые пути из [исследования #2](api-findings.md).
2. Реальный Product и подключение к детерминированному нормализатору #2.
3. Проверка выбранной модели с настроенным `OPENAI_API_KEY` на очищенных реальных записях.

API-вызов опирается на [официальный контракт Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Отказы и незавершённые ответы обрабатываются отдельно от schema validation.

Независимое ревью отдельным агентом проверило границу авторитетности данных. Выявленные
пробелы общего таймаута чтения и ограничения размера проекции исправлены и покрыты
регрессионными тестами; повторное ревью не выявило блокирующих замечаний. Это ревью кода,
а не подтверждение точности модели на реальных товарах.
