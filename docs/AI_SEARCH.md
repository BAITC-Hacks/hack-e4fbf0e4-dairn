# Поиск кандидатов по пользовательскому тексту

`POST /api/catalog/assist/search` соединяет Ktor, нормализованный каталог и OpenAI Responses API.
Клиент отправляет одну строку. Сервер выполняет ограниченную последовательность из двух
AI-вызовов; автономного цикла, доступа модели к HTTP-инструментам или raw EKT нет.

1. OpenAI извлекает цель (поиск/аналоги/уточнение), явно указанные ID/артикул,
   текстовые поисковые фрагменты и требования пользователя.
2. Kotlin проверяет строгую структуру и наличие извлечённых значений в исходной строке.
3. Каталог разрешает ID/артикул в нормализованный товар. При отсутствии в выборке
   возвращается явный статус; артикул не подменяется ID.
4. Kotlin формирует до 20 кандидатов из загруженной выборки, ранжируя по текстовым совпадениям
   с запросом и названием исходного товара. Для аналогов исходный ID исключается.
5. OpenAI выбирает до пяти ID, объяснение и точную цитату из предоставленного названия.
6. Kotlin проверяет ID по переданному набору и цитату по названию, повторно читает каталог
   через его кеш. Все возвращаемые цены, наличие, ссылки и названия берутся из каталога.
   Исчезнувший товар или изменённые name/sku кандидата приводят к явной ошибке.

Первый вызов получает только пользовательскую строку. Второй — строку, извлечённые требования,
ID/sku/name исходного товара и кандидатов. Заголовки EKT, ключи, raw JSON, цены и остатки
модели не передаются. Имена сокращаются до 1000 символов, sku — до 300 для этого контекста.

## Граница готовности

Сервис уже реализован и проверен с подменённым OpenAI-транспортом/ответами в тестах.
Живая проверка модели не выполнена: в среде разработки нет OPENAI_API_KEY и OPENAI_MODEL.

Пока источник — только изученная первая страница каталога. Ни название товара, ни мнение
AI не доказывают техническую совместимость. Ответ всегда содержит `verifiedAnalogs=false`,
`compatibility=UNVERIFIED`, `requirementsVerified=false`. Ценовой лимит, количество,
технические параметры и наличие сохраняются как **пожелания**, но выполнение их не подтверждается.
`aiReason` — непроверенное объяснение модели, а `nameEvidence` — лишь цитата названия;
это не отдельная проверенная характеристика. Отображать их как обычный текст.

Для готовых аналогов нужны подтверждённые характеристики, критерии сравнения выбранной
категории и актуальное наличие из #2. Текущий поиск не закрывает этот обязательный сценарий.
GET `/products/{id}/analogs` сохраняет явный отказ по нехватке данных.

## Запуск

В Bash из корня проекта задайте ключ локально, без передачи в чат/аргументы команд:

```bash
read -r -s -p 'OpenAI API key: ' OPENAI_API_KEY
echo
read -r -p 'OpenAI model supporting Structured Outputs: ' OPENAI_MODEL
export OPENAI_API_KEY OPENAI_MODEL
export OPENAI_SEARCH_ENABLED=true
export CATALOG_SOURCE=snapshot
export CATALOG_SNAPSHOT_PATH=catalog-service/local-evidence/products-page-1.json
gradle :catalog-service:runServer
```

Для EKT live вместо snapshot задайте `CATALOG_SOURCE=live` и переменные EKT согласно README.
CLI используется для исследования/экспорта; сервис вызывает общий Kotlin-адаптер напрямую,
не запускает shell-команды и не разбирает stdout CLI.

`OPENAI_SEARCH_ENABLED=false` по умолчанию. Флаг `OPENAI_PREVALIDATION_ENABLED` независим:
он не включает и не выключает этот поиск. Модель выбирается явно через OPENAI_MODEL.
OpenAI клиент общий с предвалидацией: `store=false`, без редиректов/повторов, лимит ответа
256 KiB, входа 64 KiB, OPENAI_TIMEOUT_MS=30000 на один вызов, OPENAI_MAX_OUTPUT_TOKENS=2048.
До двух одновременных поисков на процесс; лишний получает 429 без нового AI-вызова.
Нет сохранения диалога, истории сообщений или автоматического выполнения AI-инструкций.

## Запрос

```sh
curl -sS http://127.0.0.1:8080/api/catalog/assist/search \
  -H 'Content-Type: application/json' \
  --data '{"text":"Нужен аналог артикула 200300273_, желательно дешевле"}'
```

Тело — ровно объект с полем `text`, никаких дополнительных полей. Размер до 8192 байт,
строка после trim — 1–2000 символов без управляющих символов. Чтение тела ограничено 5 секундами.
Не включать credentials и посторонние персональные данные в пользовательский текст.

## Ответ

HTTP 200 имеет поля:

| Поле | Смысл |
| --- | --- |
| status | Один из статусов ниже |
| interpretation | purpose, productId, sku, terms[], requirements[], clarification |
| sourceProduct | Товар из каталога по явно заданному ID/SKU или null |
| candidates[] | product, aiReason, nameEvidence, compatibility, requirementsVerified |
| metadata | Источник/охват/актуальность из [Catalog API](API.md), либо null при уточнении |
| consideredProducts | Число переданных второму вызову товаров (до 20) |
| verifiedAnalogs | Всегда false в текущей версии |

Статусы:

- `CLARIFICATION_REQUIRED`: недостаточно входной информации, вопрос в interpretation.clarification;
  второй AI-вызов и загрузка каталога не выполняются.
- `SOURCE_NOT_IN_LOADED_SAMPLE`: явный ID/артикул не найден; это не доказательство отсутствия в EKT.
- `SOURCE_AMBIGUOUS`: явные идентификаторы не выделяют один товар (например, дубли SKU).
- `CANDIDATES_FOUND`: найдены только потенциальные кандидаты.
- `NO_CANDIDATES_IN_LOADED_SAMPLE`: модель не выбрала кандидатов в предоставленном наборе;
  нельзя делать вывод об отсутствии аналогов во всём EKT.

Интерпретация запроса остаётся результатом AI, не гарантией полного понимания пользователя.
Извлечённые terms/requirements/идентификаторы должны встречаться в исходной строке;
неизвестные поля и придуманные факты в ответе модели отклоняются.

## Ошибки

Общий JSON-формат `{error: {code, message}}`, без сообщений исключений и секретов:

| HTTP | code |
| --- | --- |
| 400 | INVALID_AI_QUERY — неверный ввод или недопустимые выбранные данные |
| 413 | AI_REQUEST_TOO_LARGE |
| 429 | AI_BUSY |
| 503 | AI_DISABLED |
| 503 | AI_UNAVAILABLE — конфигурация, сеть, таймаут, HTTP-ошибка провайдера |
| 502 | AI_INVALID_RESPONSE — отказ, незавершённый ответ, нарушение структуры/проверки ссылок |

Ошибки каталога сохраняют коды из API.md. Сбой OpenAI не становится пустым успешным результатом.
Обычный GET-поиск каталога продолжает работать независимо от OpenAI.

Основа протокола: [официальная документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Схема проверяет форму ответа; истинность товарных фактов обеспечивает повторное чтение каталога,
а не соответствие JSON Schema.
