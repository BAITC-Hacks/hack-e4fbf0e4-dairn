# Catalog API

Единый источник клиентского контракта для Issues #3 и #4.

## Статус

Реализован **HTTP-каркас**, а не работающий каталог. Все четыре маршрута зарегистрированы,
валидируют вход и возвращают явную ошибку неготовности. Успешных ответов с товарами пока нет.
Нормализованный Product и публичный адаптер ожидаются от #2; исходный JSON EKT не используется
как HTTP DTO. Доступность сервера не означает готовности интеграции.
Фактические результаты исследования: [api-findings.md](../catalog-service/docs/api-findings.md).
Наблюдаемая входная схема списка EKT: [EKT_DATA.md](EKT_DATA.md); она не является публичным DTO приложения.

## Маршруты и входные параметры

| GET | Назначение | Текущий ответ после валидации |
| --- | --- | --- |
| `/api/catalog/products/{id}` | Детали | 503 `CATALOG_NOT_READY` |
| `/api/catalog/products?query={query}` | Поиск | 503 `CATALOG_NOT_READY` |
| `/api/catalog/products/{id}/availability` | Наличие | 503 `CATALOG_NOT_READY` |
| `/api/catalog/products/{id}/analogs` | Аналоги | 501 `ANALOGS_NOT_IMPLEMENTED` |

`id` — непрозрачная строка длиной 1–256 символов без пробелов и управляющих символов.
Это ограничение нашего HTTP API, не подтверждённый формат EKT ID. Значение передаётся
как URL-encoded сегмент пути. Соответствие внутреннего ID внешнему ID и отличие от SKU
будут закреплены после #2; артикул нельзя автоматически считать ID.

`query` — ровно один параметр; после удаления пробелов по краям 1–200 символов без
управляющих символов. Поиск по артикулу и названию ещё не реализован.

## Ошибки

Формат `application/json`; ответы не кешируются (`Cache-Control: no-store`):

```json
{"error":{"code":"CATALOG_NOT_READY","message":"Normalized catalog adapter is not integrated yet"}}
```

Клиент использует `code`, а не текст `message`.

| HTTP | code | Состояние |
| --- | --- | --- |
| 400 | `INVALID_PRODUCT_ID` | Некорректный ID |
| 400 | `INVALID_SEARCH_QUERY` | Некорректный или повторённый query |
| 404 | `PRODUCT_NOT_FOUND` | Подтверждённое отсутствие товара; зарезервировано для адаптера |
| 404 | `ROUTE_NOT_FOUND` | Нет такого маршрута |
| 405 | `METHOD_NOT_ALLOWED` | Неподдерживаемый метод |
| 503 | `CATALOG_NOT_READY` | Адаптер ещё не подключён |
| 503 | `UPSTREAM_UNAVAILABLE` | Источник недоступен; зарезервировано |
| 502 | `UPSTREAM_INVALID_RESPONSE` | Ответ источника непригоден; зарезервировано |
| 501 | `ANALOGS_NOT_IMPLEMENTED` | Подбор ещё не реализован |
| 422 | `ANALOGS_INSUFFICIENT_DATA` | Не хватает проверенных данных; зарезервировано |
| 503 | `ANALOGS_UNAVAILABLE` | Подбор недоступен; зарезервировано |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка без раскрытия исключения |

Статусы зарезервированных ошибок проверены синтетическими HTTP-тестами. Это **не**
проверка маппинга реальных ответов EKT: преобразование ошибок адаптера ещё предстоит.
Отмена coroutine не преобразуется в 500.

## Условия подключения успешных ответов

Следующие требования обязательны, но ещё не реализованы:

- DTO используют единую нормализованную модель #2. Неизвестные значения остаются
  отсутствующими; неизвестный остаток не равен нулю, отсутствующая цена не равна нулевой.
- Описание и структурированные характеристики передаются раздельно. Заполненные
  характеристики являются основным источником параметров для большинства исследованных
  карточек. Пустой раздел характеристик не означает отсутствия сведений: часть данных
  может быть только в неструктурированном описании. Такой текст нельзя автоматически
  выдавать за подтверждённые параметры товара.
- Наличие различает подтверждённое наличие, отсутствие и неизвестность. Для кешируемых
  данных нужны источник, время получения и явный признак устаревания.
- Поиск опирается на проверенные возможности EKT. Если нужен поиск в приложении,
  перед реализацией фиксируются поля, пределы страниц/товаров/запросов/времени, обновление,
  TTL и поведение при частичной загрузке. Ответ обязательно показывает полноту охвата.
  Текущий каркас ничего не загружает и не кеширует; конкретные пределы пока не выбраны.
- Пустой результат частичного поиска не доказывает отсутствие товара у EKT.
- Аналоги требуют существующего ID, проверенных характеристик, совпадений, существенных
  отличий, причины и подтверждённого актуального наличия. Критичные параметры определяются
  для категории; неизвестные значения не считаются совпадениями. Факты кандидата
  повторно валидируются через каталог. ИИ не определяет цену, остаток и характеристики.
- Корректный результат «аналогов нет» будет успешным пустым результатом только после
  выполнения подбора; он не заменяет 501/422/503. Типизированный порт AI и успешный
  DTO аналогов ещё не готовы: они зависят от Product из #2.

## Локальная проверка

JDK 21, Gradle 8.8, из корня:

```sh
gradle :catalog-service:runServer
curl -i 'http://127.0.0.1:8080/api/catalog/products/example-id'
curl -i 'http://127.0.0.1:8080/api/catalog/products?query=cable'
curl -i 'http://127.0.0.1:8080/api/catalog/products/example-id/availability'
curl -i 'http://127.0.0.1:8080/api/catalog/products/example-id/analogs'
```

`example-id` — пример запроса, не реальный товар. Ожидаются ошибки из таблицы.
Адрес по умолчанию `127.0.0.1:8080`; настройки `CATALOG_HOST` и `CATALOG_PORT`.
EKT credentials каркасу не нужны. Секреты остаются только в существующем backend-адаптере;
добавление переменных EKT само по себе не активирует интеграцию.
