# Catalog Service

Упаковка JAR, Docker/Compose, health endpoints и фактический статус проверок Issue #7:
[инструкция развёртывания](../docs/DEPLOYMENT.md).

Сервис-клиент для работы с каталогом EKT в проекте HackAlem.

## Текущий статус

Подготовлены Kotlin/JVM-клиент EKT, CLI, общий нормализатор полученной первой страницы и Ktor API. Схема списка подтверждена сохранённым образцом из 20 товаров; детали, пагинация и живые ошибки ещё не проверены. Issue #2 пока не завершён.

### Сборка и выполненная часть

Требуются JDK 21 и Gradle 8.8. Из каталога `ekt-catalog-service`:

```sh
gradle test
gradle build
```

Модуль использует Kotlin 2.1.10 и JDK HttpClient. В рамках Issue #3 добавлен Ktor 3.1.1 HTTP-каркас в том же модуле; отдельные микросервисы не вводятся.

Отдельный запуск существующего сервера: `gradle runServer` (по умолчанию `127.0.0.1:8080`, настройки `CATALOG_HOST` / `CATALOG_PORT`). Задача `run` теперь запускает CLI из Issue #2. Канонические маршруты, ошибки, примеры запросов и оставшиеся зависимости описаны в [едином API-контракте](../docs/API.md).

При явном `CATALOG_SOURCE=snapshot` сервер читает сохранённый JSON из `CATALOG_SNAPSHOT_PATH`; при `CATALOG_SOURCE=live` использует существующий EKT-клиент и настроенные credentials. По умолчанию источник выключен. Реализованы карточка по данным списка, поиск по артикулу/названию в загруженных страницах и ответ о неизвестном наличии. Live-загрузка ограничена `CATALOG_MAX_PRODUCTS` (100) и `CATALOG_MAX_PAGES` (10), останавливается на пустой странице и кешируется. Поиск «автомат» учитывает наблюдаемые сокращения `АВ DRX…` и `Диф.авт.`; ответ содержит `matchedProducts` и предупреждение `PARTIAL_CATALOG_SEARCH`. Охват всегда помечен как частичный; время получения snapshot неизвестно. Подбор аналогов блокируется отсутствием проверенных характеристик и наличия. [Запуск на полученном JSON и API-контракт](../docs/API.md).

- `EktConfig.fromEnvironment()` проверяет обязательные переменные, HTTPS origin и формат credentials; строковое представление скрывает конфигурацию.
- Внутренний `EktRawClient` вызывает только известные GET endpoints; `id` кодируется как query parameter.
- HTTP-клиент запрещает редиректы, ограничивает подключение 10 секундами, запрос 30 секундами, успешный ответ 8 MiB.
- Ошибки конфигурации, запроса, авторизации, HTTP, транспорта и разбора JSON представлены явно. Тела ответов и credentials не включаются в сообщения исключений.
- Транспортные и CLI-тесты используют синтетические ответы. Тесты нормализатора/API дополнительно используют проверенную копию полученной первой страницы; это не подтверждает схему деталей или живую аутентификацию.

`EktRawClient` имеет видимость `internal`: его JSON-результат не является контрактом для Backend/AI. Общая модель `model.Product` и граница `NormalizedCatalog` используют `EktListNormalizer`, основанный на наблюдаемой странице. Детали и дополнительные поля будут добавлены после исследования; схема деталей не предполагается по схеме списка.

### Что необходимо для продолжения

В актуальном Issue #2 партнёрский адрес указан как `https://ekt.kz`. Партнёр выдал логин/пароль автору задачи; это не означает, что они автоматически доступны текущему процессу. Настроить `EKT_API_BASE_URL=https://ekt.kz`, `EKT_API_USERNAME`, `EKT_API_PASSWORD` в окружении процесса либо воспользоваться интерактивным запускником ниже. Базовый URL указывается без `/api`: известные пути добавляет клиент.

Файл `.env.example` в каталоге сервиса содержит адрес EKT и пустые placeholders для credentials. Локальные `.env` и `.env.*` игнорируются Git; модуль сам не загружает `.env`. Не передавайте пароль в чат, аргументах команд, тестовом выводе или документации. Для локальных ответов исследования зарезервирован игнорируемый каталог `local-evidence/`; публикуемые fixtures следует отдельно проверить на отсутствие секретов.

До исследования положительный номер страницы — только локальное ограничение клиента, а не утверждение о нумерации страниц EKT. Классификация HTTP 401/403/404 также является поведением клиента; фактические ответы EKT ещё предстоит записать. JSON-ошибки внутри HTTP 200 можно будет распознать только после проверки схемы.

План исследования и оставшиеся результаты: [docs/api-findings.md](docs/api-findings.md).

### CLI: получение данных из терминала

Установите JDK 21. В репозитории есть wrapper Gradle 8.8: вместо `gradle` можно использовать `sh ./gradlew`. Все команды ниже выполняются из каталога `ekt-catalog-service`. CLI не запускает Ktor и не скачивает весь каталог автоматически.

Для ввода выданных логина и пароля непосредственно при запуске:

```sh
gradle --quiet installDist
bash bin/ekt-cli list --page 1 --output local-evidence/products-page-1.json
bash bin/ekt-cli list --page 2 --output local-evidence/products-page-2.json
bash bin/ekt-cli detail --id '<real-product-id>' --output local-evidence/product-detail.json
```

Замените `<real-product-id>` на ID из полученного списка. Bash-запускник использует `https://ekt.kz` по умолчанию, запрашивает недостающие login/password через терминал, скрывает пароль и передаёт значения существующему Kotlin CLI только через окружение. Ввод не записывается в историю команд или файлы; credentials сохраняются лишь на время процесса. При следующем запуске потребуется повторный ввод, если переменные не экспортированы заранее. Пароль нельзя передавать аргументом. Без терминала используйте заранее настроенное окружение; запрос ввода завершается безопасной ошибкой с кодом 2. `--help` не запрашивает credentials. Пути экспорта разрешаются от текущего каталога терминала. Прямой `gradle ...:run` сам credentials не спрашивает — для него используйте настройку окружения ниже.

Справка работает без конфигурации и сети после установки зависимостей сборки:

```sh
gradle --quiet run --args='--help'
```

Безопасная интерактивная настройка в Bash (ввод пароля скрыт; его значение не попадает в командную строку или историю):

```bash
set +x
export EKT_API_BASE_URL=https://ekt.kz
read -r -p 'EKT username: ' EKT_API_USERNAME
read -r -s -p 'EKT password: ' EKT_API_PASSWORD
printf '\n'
export EKT_API_BASE_URL EKT_API_USERNAME EKT_API_PASSWORD
```

Создание `.env` само по себе **не настраивает CLI**: загрузка `.env` не реализована. Конфигурация читается через `EktConfig` из окружения процесса. Credentials не нужно передавать в чат.

```sh
gradle --quiet run --args='list'
gradle --quiet run --args='list --page 1'
gradle --quiet run --args='list --page 2'
gradle --quiet run --args='detail --id <real-product-id>'
gradle --quiet run --args='list --page 1 --output local-evidence/products-page-1.json'
```

Замените `<real-product-id>` настоящим ID, полученным из списка. `list` вызывает `/api/products`, `--page` добавляет параметр страницы, `detail` вызывает `/api/products/detail?id=...` с кодированием ID. `--output` доступен обеим командам. Номер страницы должен быть положительным целым; неизвестные/повторные опции и отсутствующие значения отклоняются до запроса.

Задача Gradle `run` явно использует каталог `ekt-catalog-service` как рабочий каталог, поэтому относительный путь из примера не удваивает `ekt-catalog-service/`.

Для чистого stdout без сообщений сборки используйте установленный дистрибутив:

```sh
gradle --quiet installDist
build/install/ekt-catalog-service/bin/ekt-catalog-service --help
build/install/ekt-catalog-service/bin/ekt-catalog-service list --page 1
build/install/ekt-catalog-service/bin/ekt-catalog-service detail --id '<real-product-id>' --output local-evidence/product-detail.json
```

Дистрибутив разрешает относительные пути от текущего каталога терминала. Без `--output` stdout содержит только успешный JSON, stderr — операцию, результат и HTTP status, если он получен. HTTP-статус доступен и при отклонении полученного JSON; при таймауте/сетевой ошибке его может не быть. Успешный JSON сохраняет исходные поля, значения и форматирование; в конце добавляется перевод строки. Это локальный raw-экспорт для исследования, **не** Product-контракт для Issue #3 или AI. До проверки схемы HTTP 200 с JSON-объектом означает успешное получение данных, но не доказательство, что объект содержит товары, а не прикладную ошибку EKT.

С `--output` stdout пуст, родительские каталоги создаются только после успешного получения JSON. Полный UTF-8 файл публикуется без перезаписи через hard link из временного файла в том же каталоге; временный файл удаляется. Требуется файловая система с поддержкой hard links, иначе возвращается ошибка. Существующие файлы, каталоги и символические ссылки не заменяются; выбирайте новое имя для каждого наблюдения. Не используйте shell-перенаправление `> evidence.json`, если требуется защита от перезаписи: оно обходит гарантии `--output`.

| Код CLI | Значение |
| --- | --- |
| 0 | Успех / справка |
| 2 | Ошибка аргументов или конфигурации |
| 3 | Ошибка EKT, сети, таймаут или невалидный JSON |
| 4 | Ошибка записи/доступа, существующий файл, неподдерживаемый экспорт |
| 1 | Непредвиденная ошибка с безопасным сообщением |

Эти коды возвращает исполняемый дистрибутив. Gradle считает ненулевой код дочернего процесса ошибкой задачи и может вернуть собственный код 1; для автоматизации используйте дистрибутив. Диагностика не печатает ID, пути вывода, credentials, Authorization, произвольные исключения или тела ошибок источника. Raw JSON намеренно направляется только в выбранный пользователем вывод; перед передачей/коммитом его нужно отдельно проверить. `local-evidence/` уже игнорируется Git.

После работы можно удалить credentials из окружения текущего shell:

```sh
unset EKT_API_BASE_URL EKT_API_USERNAME EKT_API_PASSWORD
```

Нельзя считать подтверждёнными наличие или семантику следующих данных, пока они не проверены по реальным ответам API:

- цена;
- наличие и остаток на складе;
- артикул/SKU;
- характеристики;
- сертификаты;
- производитель и бренд;
- изображения и описания.

Issue 2 является источником задач по подключению и проверке API. Issue 1 определяет архитектурные границы и требования к достоверности данных.

## Назначение

`ekt-catalog-service` должен предоставлять Backend единый безопасный адаптер для чтения данных каталога EKT.

Сервис отвечает за:

- аутентификацию в EKT API;
- получение списка товаров;
- чтение страниц каталога;
- получение деталей товара;
- нормализацию только подтверждённых API-полей;
- явную обработку ошибок и недоступности API;
- сохранение сведений о том, какие возможности EKT подтверждены, отсутствуют или не проверены.

Сервис не отвечает за:

- chat UI;
- AI-оркестрацию и генерацию ответов;
- самостоятельный выбор аналогов;
- корзину и checkout;
- хранение платёжных данных;
- публикацию EKT credentials во frontend или AI prompts.

## Предоставленный EKT API

По Issue 2 известны следующие read-only endpoints:

```text
GET /api/products
GET /api/products?page={page}
GET /api/products/detail?id={id}
```

Фактическая схема ответов пока не установлена. Не следует добавлять в клиент или документацию поля, которых нет в реальных ответах EKT.

После получения доступа необходимо проверить:

1. `GET /api/products`;
2. `GET /api/products?page=1`;
3. `GET /api/products?page=2`;
4. детали нескольких существующих товаров;
5. неизвестный и некорректный `id`;
6. поведение без авторизации и с некорректной авторизацией, если это безопасно.

Для каждой проверки нужно зафиксировать HTTP status, форму ответа, пагинацию и реально присутствующие поля.

## Конфигурация

Credentials должны передаваться только через переменные окружения:

```text
EKT_API_BASE_URL=
EKT_API_USERNAME=
EKT_API_PASSWORD=
```

Значения не должны попадать в Git, логи, frontend, документацию или промпты AI. В репозитории допускается только безопасный `.env.example` с пустыми значениями или placeholders.

Backend — единственный компонент, который напрямую аутентифицируется в EKT API.

## Граница данных

Поток данных должен выглядеть так:

```text
Frontend / AI
      |
      v
Backend API
      |
      v
Catalog Service
      |
      v
EKT Catalog API
```

AI не является источником истины для цены, наличия, характеристик или сертификатов. Эти значения должны поступать через Backend и Catalog Service из EKT либо быть явно помечены как недоступные.

## Планируемый адаптер

Минимальный клиент должен иметь операции, соответствующие подтверждённым EKT endpoints:

```text
listProducts(page?)
getProductDetails(id)
```

Результат адаптера должен различать:

- успешный ответ;
- ошибку авторизации;
- ошибку валидации запроса;
- отсутствие товара;
- недоступность EKT API;
- неизвестную или несовместимую схему ответа.

Клиент не должен молча возвращать пустые, дефолтные или выдуманные значения при ошибке API.

Публичные DTO для Backend следует определить после проверки реальных ответов. До этого нельзя фиксировать названия полей и их типы как окончательный контракт.

## Неподтверждённые возможности

Из известных endpoints пока нельзя утверждать поддержку следующих операций:

- полнотекстовый поиск товаров;
- поиск аналогов;
- чтение корзины;
- изменение корзины;
- checkout или получение ссылки на корзину;
- отдельный endpoint сертификатов;
- отдельный endpoint актуального stock.

Если эти возможности отсутствуют в предоставленном API, они должны быть оформлены как integration gaps. Catalog Service не должен изобретать недокументированные EKT endpoints.

## Проверка готовности

Интеграция считается проверенной, когда выполнены все условия:

- credentials читаются из environment variables;
- запрос списка товаров успешно выполняется;
- проверены страницы 1 и 2;
- проверены детали нескольких реальных товаров;
- документированы реальные поля и пагинация;
- проверен хотя бы один безопасный failure case;
- ошибки клиента явные и не подменяются фиктивными данными;
- credentials отсутствуют среди отслеживаемых файлов;
- raw responses и нормализованные значения согласованы.

До выполнения этих проверок сервис имеет статус `unverified`.

## AI-предвалидация (Issue #5)

Разбор пользовательской строки и поиск кандидатов реализованы отдельно от предвалидации:
[AI-поиск — настройка и контракт](../docs/AI_SEARCH.md). Метод `POST /api/catalog/assist/search`
использует нормализованный каталог и два ограниченных вызова OpenAI; результаты помечаются
как непроверенные кандидаты, не как взаимозаменяемые аналоги.

Добавлен независимый Kotlin-клиент OpenAI для рекомендательной проверки выбранных полей сырой записи. Он сохраняет исходные данные отдельно от строгого отчёта, отклоняет некорректный AI-ответ и возвращает явный статус при сбоях. По умолчанию выключен; не подключён автоматически к CLI или Ktor. Реальные fixtures и интеграция с нормализатором ожидают #2.
